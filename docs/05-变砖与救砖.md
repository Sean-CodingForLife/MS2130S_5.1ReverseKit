# 变砖与救砖

> 事故、Linux usbfs 救砖与硬规则。对应原文第 13、14 节。变砖固件单独放在 `firmware/danger/`，禁止刷。

## 事故

为了让 Windows 只能选到 alt3，`patch_alt3.py` 把 alt1、alt2 的 `bNumEndpoints` 从 `01` 改成 `00`，但保留了它们后面的 endpoint 描述符。Windows 的 USB 核心要求 `bNumEndpoints` 与实际跟随的端点数量一致，不一致就拒绝整个配置描述符。

症状：

```
设备管理器  Unknown USB Device (Invalid Configuration Descriptor)
InstanceId  USB\VID_0000&PID_0006\...
HardwareIds USB\CONFIGURATION_DESCRIPTOR_VALIDATION_FAILURE
ProblemCode 43
```

所有接口（包括刷写用的 HID）一起消失。

## 为什么 Windows 侧无解

- 设备连 VID/PID 都没上报，硬件 ID 就是 `USB\CONFIGURATION_DESCRIPTOR_VALIDATION_FAILURE`
- 没有接口 → 没有 HID → `ms213x_flash.exe`（hidapi）找不到设备
- 没有 VID/PID → Zadig / WinUSB / usbipd 都枚举不到 → 无法走裸控制传输

## 为什么 Linux 侧可行

Linux 的 USB 核心对这种不一致只是警告并忽略多余的端点，设备照常注册：

```
found 345f:2132 (MS2130S)  bus 2 addr 2  'USB3 PLUS Video'
```

于是可以用 `/dev/bus/usb` + `USBDEVFS_CONTROL` 直接发 HID 类控制传输，不需要 hidapi、不需要驱动。

## 救砖流程

1. Ubuntu 24.04 启动盘（Rufus，ISO 模式，GPT+UEFI），选 `Try Ubuntu`
2. 解绑 usbhid 占用的接口：

```bash
cd /sys/bus/usb/drivers/usbhid
echo -n *:1.4 | sudo tee unbind
```

3. 刷回原厂：

```bash
cd /cdrom/ms213x-restore
sudo python3 ms213x_restore.py probe
sudo python3 ms213x_restore.py restore ms2130s_backup.bin
```

成功标志：`claim interface 4: ok`、`header magic 3C C3 -> OK`，最后 `cmp -l` 核对 98356 字节全等。

脚本源文件是 `tooling/reverse/ms213x_restore.py`，纯标准库、走 usbfs。

## 踩过的坑

| 现象 | 原因 | 解法 |
|---|---|---|
| `disconnect driver: Inappropriate ioctl for device` | 新内核废弃 `USBDEVFS_DISCONNECT` | 改用 sysfs unbind |
| `claim interface 4: Device or resource busy` | `usbhid` 占着接口 4 | `echo -n *:1.4 > .../usbhid/unbind` |
| `echo -n 2-1.2:1.4 > unbind` 报 `No such device` | 接口名猜错 | 用 `*:1.4` 通配，实际是 `2-1:1.4` |
| `sh: Syntax error: newline unexpected` | 长命令粘贴被换行截断 | 一次只贴一条短命令 |
| `VERIFY FAILED` 但 `cmp` 显示 0 差异 | 脚本整页读回 385×256=98560 字节，与 98356 字节文件比 | `return bytes(buf[:total])` |
| GUI 花屏 / “Oh no! Something has gone wrong” | 显卡驱动问题，与任务无关 | `Ctrl+Alt+F3` 走文字终端 |

## 性能

Linux usbfs：擦除 + 写 98356 字节 + 全片回读比对约 1 分钟。

Windows hidapi：约 6 分钟。差距来自每次控制传输的开销。

## 五条红线

1. **只改格式字段可以反复试；改 `bNumEndpoints`、增删描述符是单向操作。** 结构不合法会让 Windows 拒绝整个配置描述符，连 HID 刷写通道一起消失。
2. **刷写过程中不能拔 USB。** 刷完必须真断电，芯片只在启动时从 flash 加载描述符。
3. **每次改描述符必须同时改序列号。** Windows 按设备实例缓存音频端点格式，不改序列号会一直沿用旧端点。
4. **插 USB 2.0 口会走未改动的原厂配置，退回 2ch，不会损坏。** 这也是 USB3 配置改坏后的退路。
5. **`firmware/danger/ms2130s_alt3only.bin` 是变砖固件，不要刷。** 它把 alt1/alt2 的 `bNumEndpoints` 置 0 却保留端点描述符，lint 报 4 处错误。

## 教训

这次变砖的根因不是技术难点，是验证层次错位：断偏移、算校验和、读回比对只能证明“字节写对了”，不能回答“主机还认不认得这个描述符”。

- 改动要分级：格式字段最坏仍能枚举；接口与端点的结构关系是单向操作。
- 刷前必须过 lint。`uac_desc_lint.py` 按 `bLength` 走一遍配置描述符，检查 `bNumEndpoints` 与实际端点数量。原厂 0 错；坏补丁直接打 4 行错误。这 30 行代码是事故唯一缺失的一环。
- 能不改固件就不改。本轮该先做的是在 Linux 里发一次 `SET_INTERFACE(alt=3)`，只读实验，零变砖风险。
- 写入脚本必须先自证：用已知文件跑通“读 → 比对 → 报告差异字节数”，再碰真数据。
