# MS2130S 采集卡 5.1 声道逆向 —— 现状简报

## 1. 背景

目标：让一块 56 元的公模 MS2130S USB 采集棒能录出真正的 5.1 声道（Nintendo Switch 2 输出 LPCM 5.1）。
厂商规格书写的是「USB 音频默认 48kHz/24bit 立体声输出，支持 5.1 声道模式」。
本简报记录目前已完成的实验、证据与卡点，供外部协助分析。

---

## 2. 硬件与固件概况

- 设备：USB 采集棒，`VID_345F / PID_2132`，产品名 `USB3 PLUS`
- Windows 内 EDID 名称：`HD TO USB`（EDID 厂商码 HJW2130）
- 芯片：宏晶微 MS2130S（8051 内核 + 外挂 SPI Flash）
- 固件镜像：98356 字节 = header 0x30 + code 0x18000 + 校验 4 字节；代码分 3 个 0x8000 bank
  - 头部校验 `0x24DC`，代码校验 `0xD9B8`（已核对一致）
  - 固件日期 `2025-08-26`
- EDID 位于镜像 `0x2F8`：`LPCM 8ch`，CEA-861 rev3
  - 实测：NS2 接到该卡后，音频设置里 5.1 各声道**不显示 ❗**，说明 NS2 确实在发送 5.1 LPCM
- 刷写通道：厂商 HID 接口 `HID\VID_345F&PID_2132&MI_04`，feature report，无需替换驱动
- 寄存器访问：HID 命令 `0xb5/0xb6` 读写 XDATA 字寄存器；`0xc5/0xc6` 读写 SFR
  - 注意：读回的数据位于响应缓冲区 `buf[4]`（不是 buf[3]）

---

## 3. 原厂固件里的音频描述符（关键）

存在两套完整配置（USB2 @0x640、USB3 @0xA94），音频结构完全镜像：

```
alt1  @0x9E8 : 0B 24 02 01 02 03 18 01 00 77 01   2ch / 24bit / 96kHz
       endpoint @0x9F3: 09 05 82 05 40 02 04 00 00   wMaxPacketSize=576, bInterval=4

alt2  @0xA13 : 0B 24 02 01 02 02 10 01 80 BB 00   2ch / 16bit / 48kHz
       endpoint @0xA1E: 09 05 82 05 C0 00 04 00 00   wMaxPacketSize=192

alt3  @0xA3E : 0B 24 02 01 06 02 10 01 80 BB 00   6ch / 16bit / 48kHz   ← 厂商自带 6ch
       endpoint @0xA49: 09 05 82 05 40 02 04 00 00   wMaxPacketSize=576
```

USB3 配置镜像位于 `0x1064 / 0x1095 / 0x10C6`，端点后还多 6 字节 SS companion（`06 30 ...`）。

AudioControl 侧（两套配置相同）：

```
输入终端  0C 24 02 03 02 06 00 06 03 00 00 06   bNrChannels=6, wChannelConfig=0x0003
Feature   0E 24 06 0B 03 01 01 00 ...            7 个控制（master + 6ch）
```

结论：**整条描述符链本来就是按 6 声道准备的**，不是 2 声道设备。

## 4. 实验与结果

### 实验 A：改描述符，强制 6 声道

改动（两套配置各一份，共 4 处）：

1. alt1 格式 `0B 24 02 01 02 03 18 01 00 77 01` → `0B 24 02 01 06 02 10 01 80 BB 00`
2. alt2 格式 `0B 24 02 01 02 02 10 01 80 BB 00` → 6ch，端点包长 192 → 576
3. 输入终端声道掩码 `03 00` → `3F 00`
4. 改 USB 序列号便于强制新建端点（Windows 对同实例会复用缓存的端点格式）

结果：

- Windows **成功识别为 6 声道端点**，OEMFormat = `6ch/48000/16bit`，WASAPI mix format = `6ch`
- 但抓到的数据是：

```
std = 0.5772 (= 1/√3),  lag-1 自相关 ≈ 0.002,  P(|x|<0.5) ≈ 0.501
→ 均匀分布白噪声（未初始化 SRAM 随机值）
```

- 60 秒游戏抓取：六通道 RMS **恒定 0.58**，完全不随时间/内容变化
- 对照组（虚拟声卡回环，播放自生成的 8 声道测试音）：`peak=0.250`、`lag-1≈0.999`、`P(|x|<0.5)≈0.5` 但信号是干净正弦 → **采集代码本身没问题**

### 实验 B：NS2 自带“输出测试”

NS2 的「输出测试」会在 L / R / C / SW / SL / SR 六个喇叭上依次播放白噪声（每段约 3.5 秒）。
采集结果（阈值 15% 峰值）：

```
10.1-13.2s → ch0 + ch3
14.1-17.2s → ch1 + ch4   (ch2/ch5 微弱 0.06)
18.2-21.3s → ch1 + ch4
22.2-25.3s → ch1 + ch4
26.3-29.4s → ch0 + ch3
30.3-33.4s → ch0 + ch3
```

- 六段测试音只落在 **2 组通道**上
- 配对关系是 `ch0↔ch3`、`ch1↔ch4`、`ch2↔ch5`，**间隔正好 3**
- 六段频谱完全一致（质心 ~12kHz、>3kHz 占 87%），都是同一种白噪声
- 该结构符合「设备实际按 3 通道送、主机按 6 通道读」的交错特征

## 5. 静态分析发现

### （1）描述符不由固件代码搬运

在固件镜像里搜索 `MOV DPTR,#imm16`（字节模式 `90 hi lo`）指向各描述符地址：

```
0x0640 config A      0 refs
0x0A94 config B      0 refs
0x09E8 alt1 format   0 refs
0x0A3E alt3 format   0 refs
0x1064 alt1 format   0 refs
0x10C6 alt3 format   0 refs
0x19E7 string table  0 refs
0x1A91 device desc   0 refs
0x1AA6 device desc   0 refs
```

→ **USB 描述符由 SIE 硬件直接从 flash 固定区域读取**，固件只负责初始化与控制逻辑。
这也解释了为什么改描述符后 Windows 能立刻识别出 6 声道端点。

### （2）XDATA 静态写入扫描

扫描 `MOV DPTR,#0xFxxx` 且附近有 `MOVX @DPTR,A` / `MOVX A,@DPTR`：

- 共 **309 个写入点，200 个不同地址**
- 分布：`0xF0xx:39  0xF1xx:16  0xF2xx:5  0xF5xx:4  0xF6xx:28  0xF7xx:20  0xFCxx:13  0xFDxx:1  0xFExx:74  0xFFxx:3`

### （3）XDATA 全空间 dump（已保存 0xF000-0xFFFF）

当前值里较可疑的：

```
0xF00E = 0x3F   ← 6 个 bit 全置位（5.1 通道掩码？）
0xF00B = 0x07   ← 3 个 bit（I2S SD0/SD1/SD2 使能？）
0xF06C = 0x06
0xFC05 = 0x06
0xFC03 = 0x20
0xFE00-0xFE67   连续 104 字节全为 0x01（模块使能表？）

部分被静态扫描命中、且当前值非平凡的寄存器：

```

0xF014=23  0xF015=14  0xF016=40  0xF024=01  0xF025=80  0xF050=01  0xF051=01
0xF052=75  0xF054=01  0xF061=6D  0xF065=08  0xF06C=06  0xF06D=20  0xF084=80
0xF0B0=1C  0xF0B1=F1  0xF0B6=DF  0xF0B8=1F  0xF0B9=10  0xF112=96  0xF11C=80
0xF141=80  0xF142=D1  0xF143=F0  0xF144=08  0xF145=24  0xF149=5C  0xF14A=DD

## 9. 补充：2ch vs 6ch 的 XDATA 差量（2026-11-13 凌晨新增）

方法：在两种固件状态下各做一次 0xF000-0xFFFF 全空间 dump，再做差量。
为剔除动态寄存器，2ch 状态连续 dump 两次，只保留「6ch 与两次 2ch 都不同」的地址。

结果：**19 个寄存器稳定不同**，其中 8 个在两次 2ch dump 之间也在变（动态/视频状态，需排除）。
剩下的稳定候选：

```
0xF025 : 6ch=0x80   2ch=0x40 / 0x40      （单 bit 差异）
0xF084 : 6ch=0x80   2ch=0x40 / 0x40      （单 bit 差异，与 0xF025 同模式）
0xF0B0 : 6ch=0x1C   2ch=0x0C / 0x0C      （bit4 差异）
0xF0C0 : 6ch=0x0A   2ch=0x00 / 0x00
0xF0C2 : 6ch=0xF2   2ch=0x88 / 0x88
0xF0C3 : 6ch=0x76   2ch=0x75 / 0x75
0xF5B5 : 6ch=0x80   2ch=0x14 / 0x14
0xF5B6 : 6ch=0xF0   2ch=0x28 / 0x28
0xF5BE : 6ch=0x78   2ch=0x02 / 0x02
0xF706 : 6ch=0x40   2ch=0xC0 / 0xC0
0xF707 : 6ch=0x02   2ch=0x00 / 0x00
0xF77E : 6ch=0x45   2ch=0x5C / 0x5C
0xF7AC : 6ch=0xF8   2ch=0x40 / 0x40
```

被排除的动态寄存器（两次 2ch dump 之间就不同）：

```
0xF0C1, 0xF30A, 0xF30B, 0xF30E, 0xF30F, 0xF3B4, 0xF3B5, 0xF3C6, 0xF3CE
```

### 重要局限（必须在下一轮排除）

6ch 那次 dump 是在**有音频播放**时取的，两次 2ch dump 是在**无音频**时取的。
因此这 19 个差异里混入了「音频活动 vs 静音」的影响，不能直接认定为「通道数配置」。
下一轮需要做**三态对照**：

| 状态 | 条件 |
|---|---|
| A | 2ch 固件 + 无音频 |
| B | 2ch 固件 + 有音频 |
| C | 6ch 固件 + 有音频 |

`B−A` 差量 = 纯音频活动寄存器（应排除）；
`C−B` 差量 = 真正的通道数/路由配置寄存器。

### 另一条已排除的线索

`0xF00B` 与 `0xF00E` 在 2ch 与 6ch 状态下**完全相同**（`0x07` / `0x3F`），
因此它们不是「活动通道掩码」，更可能是芯片能力上限或 I2S 引脚固定的常量。

## 10. 操作备忘（给下一个接手的会话）

### 10.1 刷写固件

```powershell
& 'tools\ms213x_flash.exe' -w 'firmware\ms2130s_backup.bin'
```

- 约 6 分钟（全片擦除 + 写 + 校验），**过程中绝对不能拔 USB**；
- 刷完必须**真正断电**：拔卡身上的 USB 头（或 HUB 下行口），等 10 秒再插。
  ⚠ 拔 HUB 到电脑那根线**不算**断电 —— 带电源适配器的 HUB 仍会给下行口供电，芯片不会重启。
- 设备挂在 HUB 上时，插到机箱前置 USB-A 口曾出现「反复弹无法识别的 USB 设备」，换 USB-C 口正常。

### 10.2 读 XDATA 寄存器

```powershell
powershell -File scripts\ms213x_xdata.ps1 -Start 0xF000 -End 0xFFFF -Out xd.bin
powershell -File scripts\ms213x_regs.ps1 0xF00B 0xF00E
```

- HID 命令 `0xb5`（读）/ `0xb6`（写），值位于响应缓冲区 **`buf[4]`**（不是 buf[3]）；
- 设备可能枚举出多个 HID 接口路径（历史残留），脚本会逐个尝试，选能打开的那个；
- 单字节读写不会破坏固件，但**盲写未知寄存器有把芯片写挂的风险**，写前先读原值备份。

### 10.3 抓 6 声道音频

```powershell
powershell -File scripts\wasapi_rec6.ps1 -GuidPart <端点GUID前8位> -Seconds 10 -Out out.wav
```

- 必须走 **WASAPI**，DirectShow（ffmpeg dshow）只会给 2 声道；
- 端点 GUID 形如 `{af3c37cc-...}`，可用 `scripts\devstate.ps1` 或注册表 `MMDevices\Audio\Capture` 查；
- ⚠ **Windows 会按设备实例缓存端点的格式**：改了描述符后，必须改 USB 序列号强制新建实例，否则读到的还是旧格式。

### 10.4 播放多声道测试音

```powershell
powershell -File scripts\wasapi_play.ps1 -GuidPart <播放端点GUID前8位>
```

- 依次在 ch0~ch7 播放 400/600/.../1800 Hz 正弦，每声道 1.2 秒、间隔 0.4 秒；
- 用虚拟声卡（Virtual Audio Cable）当输出可静音自测。

### 10.5 判定「真 5.1」还是「假 6 声道」

抓到的数据做统计检验：

- 真实音频：`lag-1 自相关` 明显 > 0，且 RMS 随内容起伏；
- 未初始化 SRAM：`std ≈ 0.5772 (=1/√3)`、`lag-1 ≈ 0.002`、`P(|x|<0.5) ≈ 0.501`、RMS 长时间恒定 —— 这就是「描述符说 6ch、DMA 只填 2ch」的铁证。

## 11. 重要更正：6 声道数据不是 SRAM 噪声（2026-11-13 夜）

第 4 节「实验 A」和第 10.5 节的判断**是错的**。当时看到 `std=0.5772`、`lag-1≈0.002`、
六通道 RMS 恒为 0.58，就判定为「未初始化 SRAM」。但判据用错了层次——
**NS2 自带的扬声器测试本身就是白噪声，白噪声的 lag-1 自然也接近 0，这个判据区分不了两者。**

改用字节级分析后结论反过来。把抓到的 6 声道 WAV 去掉 WAV 头还原成原始字节流，
按不同「样本宽度 / 字节序 / 声道数」做假设，用**波形连续性（lag-1 自相关）**给每种假设打分：

```
H1  6ch/16bit LE @48k         lag1 = 0.790  0.016  0.999  0.790  0.054  0.999
H3  2ch/24bit LE @96k         lag1 = 0.999  0.999      <- 全部连续
H6  4ch/24bit LE @48k         lag1 = 0.999  0.999  0.999  0.999
H2/H6 大端假设                 lag1 ≈ 0.05  全部不连续
```

H3 和 H6 是同一批字节的两种切法（12 字节 = 4 个 24bit 样本 = 2 帧立体声），
都给出完美连续性。也就是说：

> **卡在「6 声道」状态下实际发出的是 24bit 样本，主机按 16bit 读，
> 于是把每个 24bit 样本的低 16 位当成了一个"声道"。**
> 低 16 位在 24bit 满量程信号里近似均匀分布 → `std = 1/√3 = 0.5774`。
> 这个 0.5772 是数学必然而非"随机垃圾"的证据。

旁证：样本值大量为偶数或 16 的倍数，且每 3 字节出现一个恒为 0 的字节
（正是 24bit 的低字节位），与"24bit 容器 + 16bit 有效位"的布局吻合。

**修正后的结论**：
- 「多出来的 4 个通道是 SRAM 残留」→ 不成立，是**字节错位**，不是空内存
- 但**仍未证明**卡能输出真正的 6 个独立声道

## 12. 关键机制：固件按 SET_INTERFACE 的 alt 序号选格式（2026-11-13 夜）

原厂固件里音频流接口（接口号 3）有 4 个 alt：

```
alt0  零带宽（无端点）
alt1  0B 24 02 01 02 03 18 01 00 77 01   -> 2ch / 24bit / 96kHz   端点 576
alt2  0B 24 02 01 02 02 10 01 80 BB 00   -> 2ch / 16bit / 48kHz   端点 192
alt3  0B 24 02 01 06 02 10 01 80 BB 00   -> 6ch / 16bit / 48kHz   端点 576
```

实测推导：

1. **原厂状态下 Windows 选中 alt2**：注册表 `PKEY_AudioEngine_DeviceFormat`
   = `2ch/48000/16bit mask 0x3`，2.0 录音干净。
2. 把 **alt1 的声明改成 6ch/16bit/48k** 再刷 → Windows 采用 alt1 的声明（OEMFormat 变 6ch），
   但抓到的数据是 **2ch/24bit/96k 的字节结构**（即原厂 alt1 的格式）。
3. 结论：**固件不读描述符内容，只按收到的 `SET_INTERFACE` 的 wValue（alt 序号）
   查自己写死的格式表。** 改描述符只改变 Windows 的解读方式，不改变卡实际发什么。

因此「6 声道」只可能挂在 **alt=3** 上，而**从头到尾没有任何一次让这张卡收到过 alt=3**。

补充实测：用 WASAPI 枚举独占模式格式，`6ch/48000/16`、`8ch`、`96k` 全部返回
`0x88890048`（不支持），只有 `2ch/48000/16` 返回 S_OK —— 说明 Windows 只暴露**一个** alt 的格式。

## 13. 变砖与救砖实录（2026-11-13 夜）

### 13.1 事故

为了让 Windows 只能选到 alt3，把 alt1、alt2 的 `bNumEndpoints` 改成 0，
**但保留了它们后面的 endpoint 描述符**。结果：

```
设备管理器：Unknown USB Device (Invalid Configuration Descriptor)
InstanceId：USB\VID_0000&PID_0006\6&2ACD0AB6&0&2
HardwareIds：USB\CONFIGURATION_DESCRIPTOR_VALIDATION_FAILURE
ProblemCode：43
```

Windows 的 USB 核心要求 `bNumEndpoints` 与实际跟随的 endpoint 描述符数量一致，
不一致就**拒绝整个配置描述符**，于是所有接口（包括刷写用的 HID）都不存在，
HID 刷写通道一起消失 —— 这是这类改动的致命之处。

### 13.2 Windows 侧为什么无解

- 设备连 VID/PID 都没上报，硬件 ID 就是 `USB\CONFIGURATION_DESCRIPTOR_VALIDATION_FAILURE`
- 没有接口 -> 没有 HID -> `ms213x_flash.exe`（hidapi）找不到设备
- 没有 VID/PID -> Zadig / WinUSB / usbipd 都枚举不到它 -> 无法走裸控制传输

### 13.3 Linux 侧为什么可行

Linux 的 USB 核心对这种不一致只是**警告并忽略多余的 endpoint**，设备照常注册：

```
found 345f:2132 (MS2130S)  bus 2 addr 2  'USB3 PLUS Video'
```

于是可以用 `/dev/bus/usb` + `USBDEVFS_CONTROL` 直接发 HID 类控制传输，
不需要 hidapi、不需要驱动。

### 13.4 可复用的救砖流程

1. Ubuntu 24.04 启动盘（Rufus，ISO 模式，GPT+UEFI）-> 选 `Try Ubuntu`
2. 终端里解绑 usbhid 占用的接口：
   ```
   cd /sys/bus/usb/drivers/usbhid
   echo -n *:1.4 | sudo tee unbind        # 实际接口名形如 2-1:1.4
   ```
3. ```
   cd /cdrom/ms213x-restore        # U 盘只读挂在 /cdrom
   sudo python3 ms213x_restore.py probe
   sudo python3 ms213x_restore.py restore ms2130s_backup.bin
   ```

成功标志：`claim interface 4: ok`、`header magic 3C C3 -> OK`，
最后用 `cmp -l` 核对 98356 字节全等。

### 13.5 踩到的坑（按踩到的顺序）

| 现象 | 原因 | 解法 |
|---|---|---|
| `disconnect driver: Inappropriate ioctl for device` | 新内核已废弃 `USBDEVFS_DISCONNECT` | 改用 sysfs unbind |
| `claim interface 4: Device or resource busy` | `usbhid` 驱动占着接口 4 | `echo -n *:1.4 > .../usbhid/unbind` |
| `echo -n 2-1.2:1.4 > unbind` 报 `No such device` | 名字猜错了 | 用 `*:1.4` 通配，实际是 `2-1:1.4` |
| `sh: Syntax error: newline unexpected` | 长命令粘贴时被换行截断 | 一次只贴一条短命令 |
| `VERIFY FAILED` 但其实已成功（`cmp` 显示 0 差异） | 脚本 bug：整页读回 385x256=98560 字节去和 98356 字节文件比 | `return bytes(buf[:total])` |
| GUI 花屏 / "Oh no! Something has gone wrong" | 显卡驱动问题（与任务无关） | 直接 `Ctrl+Alt+F3` 走文字终端 |

### 13.6 性能

Linux usbfs 下：擦除 + 写 98356 字节 + 全片回读比对 ≈ **1 分钟**，
比 Windows 的 hidapi 路径（约 6 分钟）快约 6 倍，因为每次控制传输开销小得多。

## 14. 教训与硬规则

这次变砖的根因不是技术难点，是**判断失误 + 验证层次错位**。

1. **我验证的是文件完整性，不是描述符合法性。**
   断偏移、算校验和、读回比对 —— 这三样都只能证明"字节写对了"，
   完全不能回答"主机还认不认得这个描述符"。

2. **改动要分级**：
   - 只改**格式字段**（`bNrChannels`、序列号、掩码、校验和）-> 最坏情况设备仍能枚举，可反复试
   - 改**接口与端点的结构关系**（`bNumEndpoints`、增删描述符）-> **单向操作**，
     失败会连带摧毁唯一恢复通道

3. **刷前必须过 lint。** `scripts/uac_desc_lint.py` 模拟主机解析器，
   按 `bLength` 走一遍配置描述符，检查 `bNumEndpoints` 与实际 endpoint 数量是否一致。
   原厂固件 0 错；那个坏补丁会直接打出 4 行错误。
   **这个检查 30 行代码，是本次事故唯一缺失的一环。**

4. **能不改固件就不改。** 运行时用控制传输能验证的，先验证。
   本轮真正该先做的是「在 Linux 里发一次 `SET_INTERFACE(alt=3)`」，
   那是只读实验，零变砖风险。

5. **脚本必须先自证。** 任何写入脚本，先用已知文件跑通
   「读 -> 比对 -> 报告差异字节数」，再碰真数据。
   本次 `read_flash` 的长度 bug 就是没做这一步的代价（误报 VERIFY FAILED）。

6. **减少用户负担**：长命令会被终端换行截断，导致反复重敲；照片回传效率极低。
   后续应改为局域网传输（台式机起 HTTP 服务，笔记本 curl 拉取 / 回传日志）。

## 16. 突破：5.1 已解锁（2026-11-14 凌晨）

结论先说：**这颗芯片确实能输出 6 个互相独立的声道**，厂商把功能做完了，
但把它挂在一个 Windows 永远不会选中的 `alt=3` 上。绕开这一点就能用。

### 16.1 关键洞见

- 固件按 `SET_INTERFACE` 的 alt **序号**查内部格式表，与描述符文本无关（第 12 节）
- Windows 只暴露**一个** alt 的格式（第 12 节实测）
- 所以要拿到 6 声道，只有一条路：**让主机别无选择，只能选 alt=3**

### 16.2 方法（关键：只改一份配置）

这张卡有两套按速度切换的描述符：

```
device desc @0x1A91  bcdUSB=0x0200   <- USB 2.0 用这套
device desc @0x1AA6  bcdUSB=0x0320   <- USB 3.x 用这套
config @0x0640  wTotalLength=1074    <- USB 2.0 配置
config @0x0A94  wTotalLength=1650    <- USB 3.x 配置
```

**只改 USB 3.x 那一份**：把接口 3 的 alt1、alt2 两个完整块（各 49 字节，含 SS companion）
整段删除，后面的描述符前移，`wTotalLength` 1650 → 1552。
USB 2.0 那份**一个字节都没动**，作为回退保险：万一日志，插 USB 2.0 口就走原厂配置，
设备照常枚举，可以刷回 —— **不需要 Linux**。

同时把序列号 `20210629` 改成 `20210624`。这一步是必须的：
Windows 的音频端点格式**按设备实例缓存**，而设备实例是按序列号生成的，
不换序列号会一直沿用旧端点，看不到新格式。

`scripts/mk_alt3_usb3only.py` 可复现这个补丁；`scripts/uac_desc_lint.py` 刷前验证。

## 17. 通道映射实测（2026-11-14 凌晨，用可控源标定）

### 17.1 方法

NS2 的测试音对六个喇叭放的是同一种白噪声，无法据频谱区分位置（第 16.4 节），
所以改用**笔记本 HDMI 输出**做可控源标定：

1. 生成 6 声道标定文件：100 Hz 正弦，逐通道依次播放（每段 1.5 秒，间隔 0.5 秒）
   `tools51/chmap_51_100Hz.wav`，顺序为 Windows 5.1 标准 `FL, FR, FC, LFE, BL, BR`
2. 笔记本 HDMI 接采集卡，输出设备配成 5.1，用 mpv 播放并循环：
   `mpv --ao=wasapi --audio-device=<HDMI> --audio-channels=5.1 --loop-file=inf --volume=100 chmap_51_100Hz.wav`
3. 台式机用 `tools51/rec51.ps1` 录 130 秒
4. 按 0.25 秒分块计算每通道 RMS，找有声片段落在哪个通道

### 17.2 结果（九轮循环完全一致）

```
源通道(标准顺序)        落到卡的通道
FL  (第1段)      ->    ch0
FR  (第2段)      ->    ch1
FC  (第3段)      ->    ch3   <-- 注意
LFE (第4段)      ->    ch2   <-- 注意
BL  (第5段)      ->    ch4
BR  (第6段)      ->    ch5
```

**卡的实际通道顺序是 `FL, FR, LFE, FC, BL, BR`，中置与低音炮次序相反。**
这不是掩码问题，是硬件/固件的数据排列；改 `wChannelConfig` 也修不了，
因为 WAVEFORMATEXTENSIBLE 只声明"有哪些扬声器"，次序由规范固定。

### 17.3 修复

用 ffmpeg 交换第 3、4 通道（用位置名 c0..c5，不依赖输入布局解析）：

```
ffmpeg -i in.wav -af "pan=5.1|c0=c0|c1=c1|c2=c3|c3=c2|c4=c4|c5=c5" -c:a pcm_s24le out.wav
```

验证：重排后，标定文件的段落序列从 `[0,3,1,5,4,2]` 变成 `[0,1,2,3,4,5]`，
与源文件顺序完全对齐 —— 说明映射正确、修复有效。

`tools51/修正通道顺序.cmd` 把 WAV 拖上去即可批量修正（已实测）。

### 17.4 NS2 测试顺序（用户确认）+ 交叉验证

用户实测确认 NS2「输出测试」的顺序是 **L, C, R, SR, SL, SW**（不是常见的 L/R/C/SW/SL/SR）。
用它把第 16.3 节的实测数据交叉对一遍：

| NS2 顺序 | 语义位置 | 实测落到通道 | 该通道由笔记本标定的含义 | 一致 |
|---|---|---|---|---|
| L  | FL  | ch0 | FL  | 是 |
| C  | FC  | ch3 | FC  | 是 |
| R  | FR  | ch1 | FR  | 是 |
| SR | BR  | ch5 | BR  | 是 |
| SL | BL  | ch4 | BL  | 是 |
| SW | LFE | ch2 | LFE | 是 |

**两种独立方法（笔记本可控源标定 / NS2 已知顺序反查）结论完全一致**：

1. 卡的通道语义**正确** —— 左声道真的进 FL，低音炮真的进 LFE，没有串位
2. 唯一差异是**排列次序**：卡按 `FL, FR, LFE, FC, BL, BR` 排，
   Windows 规范要求 `FL, FR, FC, LFE, BL, BR`，第 3、4 位对调
3. 因此交换 c2/c3 是唯一需要做的处理，且这不是猜测 —— 两条证据链共同确认

## 18. 尝试在固件里修正 FC/LFE 次序（2026-11-14 凌晨，未成功）

### 18.1 目标与设计

第 17 节确认卡的实际通道顺序是 `FL, FR, LFE, FC, BL, BR`，
与标准 `FL, FR, FC, LFE, BL, BR` 相比 FC/LFE 互换。
理想方案是在固件里改掉，这样录制端不需要任何后处理。

对照设计（关键：只变一个变量）：

| 状态 | 固件 | Windows 选中 alt | 格式 | 端口/速率 |
|---|---|---|---|---|
| A | 已解锁 | alt3 | 6ch/48k/16bit | 同一 USB3 口 |
| B | 原厂 | alt2 | 2ch/48k/16bit | 同一 USB3 口 |

两者速率、位深、端口、链路速度全部相同，只有通道数不同。

**关键细节：dump 必须在音频流打开时取。** 端点空闲时处于 alt0（零带宽），
配置不生效。实测同一状态下"空闲 dump"与"流中 dump"的哈希不同，证实了这一点。

### 18.2 结果

```
B vs B2（同状态两次 dump）   差异 8 个      <- 噪声底，读取可靠
A(6ch) vs B(2ch)            差异 273 个
排除动态值后仍然稳定不同      266 个
```

266 个稳定差异散布在 `0xF040-0xFE7F` 整个区间，涉及多处成片区域：
`0xF040-0xF065`、`0xF141-0xF151`、`0xF5xx`、`0xF6xx`、`0xF8xx`、
`0xFC00-0xFCC2`、`0xFE00-0xFE7F`（128 字节 0x01/0x00 块）。

### 18.3 结论：没有可编程的通道映射

- 差异数量与分布表明：固件切换 2ch/6ch 时**重配了整条音频通路**
  （DMA 描述符、FIFO 门限、I2S 时隙、使能位图），不是改一个开关
- **没有任何寄存器呈现 6 路排列表的结构**；`0xFE00-0xFE7F` 那段最像使能位图
- 即使找到"通道数"寄存器也解决不了次序问题 —— 顺序很可能写死在
  DMA 描述符或 I2S 布线里，没有运行时交换位

因此**放弃在固件里修正通道顺序**。要消除后处理，只能在录制端做通道映射
（软件预设），或继续用 `tools51/修正通道顺序.cmd` 后处理。

### 18.4 本轮新增材料

```

captures/xdata_2ch_streaming.bin     B 状态（2ch/48k/16b）流中 dump
captures/xdata_2ch_streaming_b.bin   B 状态第二次 dump（用于测噪声底）
```

## 19. OBS 录制链路（2026-11-14 凌晨，已验证）

OBS 33.1 实测可录 6 声道，且是**无损 PCM**：

``` 
videoh265  3840x2160  120 fps
audio pcm_s24le  48000 Hz  6 声道  channel_layout=unknown
``` 

配置要点（关键：不能让视频源带音频）：

1. 设置 -> 音频 -> 声道 = 5.1，采样率 48 kHz；
2. 视频来源（VD15 显示捕获）音频输出模式设为「无」；
3. 另加一个「音频输入采集(WASAPI)」源，设备选 USB3 PLUS Audio；
4. 高级音频属性里只勾轨道 1。

channel_layout=unknown 是卡报掩码 0 导致的，所以 OBS 按默认 5.1 顺序写文件，
FC/LFE 仍然是反的，需要每段录完做一次重排。

重排工具：	ools51/修正通道顺序_视频.cmd（拖拽视频文件，视频流直接复制不重编码）。

验证（逐样本比对，非 RMS 近似）：

``` 
原始  ch0=175271 ch1=195302 ch2=45461 ch3=38340 ch4=62982 ch5=62681
换序  ch0=175271 ch1=195302 ch2=38340 ch3=45461 ch4=62982 ch5=62681
原 ch2 == 新 ch3，原 ch3 == 新 ch2，其余通道比特级相同
``` 

注意：PCM 6ch/24bit/48k 约 864 KB/s（3.1 GB/小时），长录像可把 OBS 音频编码改成 AAC 
（重排时会重编码音频，视频仍复制）。

## 20. 结论摘要与对外分享材料（2026-11-14）

### 20.1 一句话结论

MS2130S 公版采集卡**硬件支持 6 声道**，厂商把 6 声道挂在 USB 音频接口的
`alt=3` 上，而 Windows 只会选一个 alternate setting、永远选不到它。
把 USB 3.x 配置里的 alt1/alt2 删掉（只改这一份配置，USB2 那份留作退路），
再改序列号强制 Windows 重建端点，即可录到真正的 5.1。

### 20.5 未做/未解

- **固件内修正 FC/LFE 顺序**：不可行（第 18 节，266 个稳定差异中无通道映射寄存器）
- **AC 终端掩码改 0x3F**：未做。改了只影响应用侧的"标签"，不影响数据，
  且实测会报出 `0xF03` 这种异常掩码，收益不明
- **长时间录制压测**：最长实测 130 秒，未做数小时压测
- **HDMI 分配器方案**：用户计划用分配器同时接显示器与采集卡，未验证
