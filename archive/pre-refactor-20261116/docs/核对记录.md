# 核对记录

2026-11-14 整理时做的可复现核对。能重算的都重算了；不能重算的明确标注“未复算”，不把文档里的旧数字当已验证结论。

## 一、固件镜像

### 1. 尺寸、magic、日期

- 7 个镜像全部 98356 字节：header `0x30` + code `0x18000` + 校验 4 字节。
- 头部 `0x00-0x01 = 3C C3`，`0x0D-0x0F = 19 08 1A`，对应固件日期 2025-08-26。
- 头部 `0x02-0x03 = 80 00`，`0x08-0x0B = 80 00 00 00`，对应 3 个 0x8000 bank。

### 2. 代码校验和（全部通过）

算法：`sum(blob[0x30 : len-4]) & 0xFFFF`，与末尾 2 字节（大端）比较。

| 镜像 | 存储值 | 复算 | 结果 |
|---|---|---|---|
| `ms2130s_backup.bin` | D9B8 | D9B8 | OK |
| `ms2130s_51unlock_20210624.bin` | D9CA | D9CA | OK |
| `experiments/ms2130s_6ch_patch.bin` | DBB2 | DBB2 | OK |
| `experiments/ms2130s_all6ch.bin` | DAAC | DAAC | OK |
| `experiments/ms2130s_all6ch_v2.bin` | DAAE | DAAE | OK |
| `experiments/ms2130s_alt3only.bin` | DA22 | DA22 | OK |
| `experiments/ms2130s_marker_serial.bin` | DBA0 | DBA0 | OK |

**头部校验 `0x24DC` 没有复现算法。** 对 header 48 字节做简单求和得到 `0x262A`，不是 `0x24DC`。因此简报里“头部校验 0x24DC（已核对一致）”只能理解为读到了这个字段，不能理解为算法已验证。刷写工具是否校验它、怎么校验，本轮未确认。

### 3. 解锁固件与原厂的差异

`ms2130s_51unlock_20210624.bin` 与 `ms2130s_backup.bin` 共 37 字节不同：

```
0x0A96        72 -> 10                 USB3 配置 wTotalLength 低字节（1650 -> 1552）
0x1057        01 -> 03                 alt 块搬家后的伴随字节
0x1068-0x106E 02 03 18 00 77 01 -> 06 02 10 80 BB 00   alt1 位置变成原 alt3 的格式
0x1087-0x108A 03 02 01 02 -> 04 00 03 00               描述符搬家
0x108D-0x10A3 04 07 24 01 07 00 ... -> 00 09 21 10 01 21 ...  描述符搬家
0x1A77        39 -> 34                序列号末位 '9' -> '4'（USB2 侧）
0x1A8C        39 -> 34                序列号末位 '9' -> '4'（USB3 侧）
0x18033       B8 -> CA                代码校验低字节
```

USB2 配置区 `0x0640-0x0A91` 一个字节都没动。这就是“插 USB 2.0 口可以回退”的物理依据。

## 三、XDATA 差量

### 1. 第 18 节（三态对照）——与文档一致

```
B vs B2（同状态两次 dump）    8 个差异
A vs B（6ch vs 2ch）         273 个差异
排除 B/B2 动态位后            266 个稳定差异
```

8 个噪声位：`0xF0C2、0xF30A、0xF30B、0xF30E、0xF30F、0xF3B4、0xF3B5、0xF3C6`。

**范围需要修正**：266 个稳定差异实际从 `0xF003` 开始，到 `0xFE7F` 结束，共 **63 个连续区**。简报第 18.2 节写“散布在 0xF040-0xFE7F”，漏掉了 `0xF003-0xF00C` 的 5 个差异（`0xF003、0xF004、0xF007、0xF00B、0xF00C`）。

按 256 字节区统计：

```
0xF000-0xF0FF   19 B / 10 段
0xF100-0xF1FF   15 B /  6 段
0xF300-0xF3FF    2 B /  2 段
0xF500-0xF5FF   13 B /  8 段
0xF600-0xF6FF   49 B / 14 段
0xF700-0xF7FF   10 B /  6 段
0xF800-0xF8FF   12 B /  5 段
0xFC00-0xFCFF   18 B / 11 段
0xFE00-0xFEFF  128 B /  1 段（整块）
```

合计 266 B / 63 段。其余 `0xF2xx、0xF4xx、0xF9xx-0xFBxx、0xFDxx、0xFFxx` 没有稳定差异。

### 2. 第 9 节（早期两态差量）——口径对不上

按 `xd_full` / `xd_stock` / `xd_stock2` 复算：

```
xd_full vs xd_stock        20 个差异
xd_stock vs xd_stock2       9 个动态位
排除后                     13 个稳定地址
```

13 个地址与简报列出的完全一致（`0xF025、0xF084、0xF0B0、0xF0C0、0xF0C2、0xF0C3、0xF5B5、0xF5B6、0xF5BE、0xF706、0xF707、0xF77E、0xF7AC`）。但简报写“19 个寄存器稳定不同，其中 8 个在两次 2ch dump 之间也在变”，与复算的 20 / 9 / 13 对不上。以复算为准。

### 3. 两批 dump 不可比

```
xd_full vs xdata_6ch_streaming      640 字节不同
xd_stock vs xdata_2ch_streaming     805 字节不同
xd_stock vs xdata_2ch_streaming_b   804 字节不同
```

即使都是“6ch”或“2ch”，早期批次和 11-14 流中批次也不是同一运行状态，不能直接做差量。

### 4. 两轮稳定集的交集只有 9 个

其中 6 个地址在两轮的 6ch 状态下值完全一致：

```
0xF0C3  76 / 76
0xF5B5  80 / 80
0xF5B6  F0 / F0
0xF5BE  78 / 78
0xF706  40 / 40
0xF707  02 / 02
```

3 个地址值不同：

```
0xF0B0  1C / 49
0xF77E  45 / 19
0xF7AC  F8 / D8
```

值一致的 6 个更可能是 6ch 通路的固定配置位；值不同的 3 个更像运行时状态。两组都不能单独证明“通道数开关”，但值一致的 6 个值得优先复查。

### 5. `0xF00B` 的结论要收回

- 早期 dump（`xd_full` / `xd_stock`）：`0xF00B` 都是 `0x07`，`0xF00E` 都是 `0x3F`。
- 11-14 流中 dump：`0xF00B` 在 6ch 下是 `0xFF`，在 2ch 下是 `0x43`，**不再相同**。
- `0xF00E` 在 7 份 dump 中始终 `0x3F`，可以当常量。

所以简报第 9 节“`0xF00B` 与 `0xF00E` 在 2ch 与 6ch 状态下完全相同，因此不是活动通道掩码”只对早期 dump 成立。`0xF00B` 在流中明显变化，不能据此排除。

## 四、录音复算

用标准库读取 WAV，按 0.25 秒分块计算每通道 RMS。所有关键录音都是 6ch / 48kHz / float32。

### 1. `ns2_51_unlocked_test.wav`（119.96 s）

六段扬声器测试的最大通道序列：

```
59.75-62.75 s   ch0
64.00-66.75 s   ch3
68.00-70.75 s   ch1
72.00-75.00 s   ch5
76.00-79.00 s   ch4
80.00-83.00 s   ch2
```

每段只有目标通道有能量（主体 RMS 0.046–0.067，段首尾边界块最低 0.034），其余五通道为 `0.0000`（float32 精度）。与简报 16.3 的“六段各落一个不同通道”一致；与 16.4 的 `[0,3,1,5,4,2]` 顺序一致。

段落边界与简报的 59.8–63.0 / 63.8–67.0 等略有差异，原因是分块窗口与阈值不同，落点通道不受影响。

### 2. `game_51_unlocked_5s.wav`（4.97 s）

```
ch0 0.0173   ch1 0.0116   ch2 0.0023
ch3 0.0093   ch4 0.0104   ch5 0.0037
```

与简报 16.3 一致（ch1 差 0.0001，舍入）。

### 3. `chmap_stereo_probe_sample.wav`（13.00 s）

源文件按 Windows 标准 5.1 顺序 `FL, FR, FC, LFE, BL, BR` 逐通道播放 100 Hz 正弦，录到的活动序列：

```
源第1段 FL  -> ch0
源第2段 FR  -> ch1
源第3段 FC  -> ch3
源第4段 LFE -> ch2
源第5段 BL  -> ch4
源第6段 BR  -> ch5
```

即卡的顺序是 `FL, FR, LFE, FC, BL, BR`，第 3、4 位与标准相反。与简报 17.2 一致。文件名里的 `stereo` 是误称。

### 4. `tools51/chmap_51_100Hz.wav`（13.50 s）

ch0 到 ch5 依次各 1.50 s，间隔 0.50 s，顺序正确。这是标定源，不是录音。

### 5. 对照文件

- `stock_check.wav`：2ch / 48k / float32，双通道 RMS 均为 0.000，确认原厂无音源时纯静音。
- `test6ch.wav`：6ch / **44.1k** / 16bit。采样率不是采集卡的 48k，是虚拟声卡回环。
- `vac_control.wav`：8ch / 48k / float32，Virtual Audio Cable 回环。
