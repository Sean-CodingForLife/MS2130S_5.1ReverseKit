# 如何让 MS2130S 采集卡输出 5.1 声道

> 本文记录一次逆向发现：这块 MS2130S 采集卡**硬件上支持 6 声道**，
> 但厂商把它藏在一个 Windows 永远不会选中的 USB 音频接口设置里。
> 改 37 个字节、删掉 USB3 配置里的 alt1/alt2 整块，就能把它放出来。

---

## 一、问题

常见便宜 HDMI 采集卡（MS2130S / MS2131S 芯片，56～80 元）标称"支持 5.1 声道"，
但实际接上主机后，电脑里永远只有一个 **2 声道**麦克风/线路输入端点，
HDMI 里的 LPCM 5.1 被无声地压成了立体声。

NS2 / PS5 / 蓝光机都输出 **LPCM 5.1（未压缩）**，不是 Dolby/DTS 码流。
所以只要采集卡能原样搬运 6 个通道，就能录到 6 通道环绕声。

## 二、关键发现（三条）

### 发现 1：厂商的固件里，6 声道描述符是完整的

固件里 USB 音频流接口（接口号 3）有 4 个 alternate setting：

```
alt0  零带宽（无端点）
alt1  2ch / 24bit / 96kHz
alt2  2ch / 16bit / 48kHz     <- Windows 总是选这个
alt3  6ch / 16bit / 48kHz     <- 6 声道，但 Windows 永不主动选它
```

输入终端也写着 `bNrChannels = 6`。也就是说**整条描述符链本来就是按 6 声道准备的**。

### 发现 2：固件按「alt 序号」查自己写死的格式表，不看描述符内容

这条是整件事的关键。实测：

- 把 **alt1 的描述符**改成 `6ch/16bit/48k` 再刷进卡，
  Windows 确实显示 6 声道了，但卡实际吐出来的数据是 **2ch/24bit/96k**
  —— 也就是原厂 alt1 的格式。
- 反而证明了：**固件只根据主机发来的 `SET_INTERFACE` 的 wValue（alt 序号）
  查内部固化的格式表**，描述符文本对它没有任何影响。

所以改描述符只能骗过 Windows，不能骗过卡。要拿到 6 声道，
**必须让卡真的收到 `SET_INTERFACE(alt=3)`**。

### 发现 3：Windows 只暴露一个 alt，所以 alt3 永远够不着

Windows 的 USB Audio 驱动在初始化时只取**一个** alternate setting 的格式。
实测在独占模式下请求 6ch / 8ch / 96k 全部返回 `0x88890048`（不支持），
只有 `2ch/48k/16` 成功 —— 说明它只暴露了被选中的那一个。

结论：**必须让 alt3 成为唯一可选的 streaming 设置**。

## 三、解决方案

### 3.1 妙处：这张卡有两套按速度切换的描述符

```
device desc @0x1A91  bcdUSB=0x0200   USB 2.0 用这套
device desc @0x1AA6  bcdUSB=0x0320   USB 3.x 用这套
config @0x0640  wTotalLength=1074    USB 2.0 配置
config @0x0A94  wTotalLength=1650    USB 3.x 配置
```

芯片的 SIE 按协商出的链路速度决定返回哪一套。

**只改 USB 3.x 那一套，USB 2.0 那一套一个字节都不动** —— 这就是安全网：
万一把 USB3 配置改坏导致认不出设备，把卡插到 USB 2.0 口，
它就会走那份没动过的原厂配置，设备照常枚举，可以刷回原厂固件。
**不需要 Linux，不需要编程器。**

### 3.2 具体改动（USB 3.x 配置里）

1. 删除接口 3 的 **alt1、alt2 两个完整块**（每块 49 字节，含 SS companion），
   后面的描述符整体前移
2. 把 `wTotalLength` 从 **1650 改成 1552**（减 98）
3. 改动 USB 序列号（例如 `20210629` → `20210624`）
   —— **必须改**，因为 Windows 的音频端点格式按设备实例缓存，
   而实例是按序列号生成的，不改序列号会一直沿用旧端点看到旧格式

改完之后，接口 3 只剩 alt0（零带宽）和 alt3（6ch/16bit/48k），
Windows 别无选择，只能选 alt3。

### 3.3 脚本

`tooling/reverse/mk_alt3_usb3only.py` 可复现这个补丁（输入原厂固件，输出解锁固件）。
刷写前务必用 `tooling/reverse/uac_desc_lint.py` 验证描述符结构，
它模拟主机解析器，会报出 `bNumEndpoints` 与实际端点数量不一致这类致命错误
（曾经因为这类错误把卡刷成"无法识别的 USB 设备"）。

## 四、操作步骤

### 4.0 准备

- 原厂固件备份（用 `tooling\flash\ms213x_flash.exe -r backup.bin` 读出，或找同型号同版本的固件）
- 刷写工具 `ms213x_flash.exe`（Windows，hidapi，无需驱动）
- 本仓库的 `tooling\reverse\mk_alt3_usb3only.py` 和 `tooling\reverse\uac_desc_lint.py`
- 采集卡插在 **USB 3 口**上（USB 2 口不会走改过的那份配置）

### 4.1 生成解锁固件

```bash
python tooling\reverse\mk_alt3_usb3only.py backup.bin unlocked.bin --serial 20210624
python tooling\reverse\uac_desc_lint.py unlocked.bin      # 必须 0 错误
```

### 4.2 刷写

```powershell
tooling\flash\ms213x_flash.exe -w unlocked.bin
```

约 6 分钟，工具会擦除、写入、逐字节校验。**过程中绝不能拔 USB。**

### 4.3 断电重载

刷完必须**断开卡身电源**：把卡从 USB 口拔下来，等 10 秒，再插回 USB 3 口。
（芯片只在启动时从 Flash 加载描述符。）

### 4.4 验证

Windows 的「声音设置 → 录制」里会多出一个端点，格式应为：

```
6ch / 48000 Hz / 16 bit
```

> 这是硬件端点格式。WASAPI 采集通常写 IEEE float32，修通道输出 `pcm_s24le`；三层位宽不要混用。

用任意 WASAPI 录音程序录一段，或直接看采集卡在高电平时的表现。

## 五、验证「确实是 6 个独立通道」

不要靠听感判断（音响的虚拟环绕会让 2.0 听起来也很"环绕"）。
用已知内容测试：

1. 播放主机（PC 或游戏机）的**扬声器测试**，逐喇叭出声
2. 用 WASAPI 录 6 声道
3. 按时间分块，看每一段落在哪些通道

实测数据（NS2 输出测试，顺序 L/C/R/SR/SL/SW）：

```
段落            落到的通道    其余五通道
L   -> ch0      0.0582       0.0000
C   -> ch3      0.0561       0.0000
R   -> ch1      0.0571       0.0000
SR  -> ch5      0.0577       0.0000
SL  -> ch4      0.0579       0.0000
SW  -> ch2      0.0566       0.0000
```

每段只有**一个**通道有声，其余在浮点精度下完全为零 —— 这是 6 个独立通道，
不是 2 声道复制。

## 六、一个必须处理的坑：FC 与 LFE 顺序反了

用已知顺序的多声道文件标定后，实测这块卡输出的通道顺序是：

```
卡的顺序   FL, FR, LFE, FC, BL, BR
标准 5.1   FL, FR, FC, LFE, BL, BR
                    ↑↑↑ 第 3、4 位互换了
```

**这不是掩码问题。** UAC1 规定流里通道的排列由 `wChannelConfig` 的
置位顺序（从低位到高位）决定，而 `FC` 是 bit2、`LFE` 是 bit3，
FC 永远排在 LFE 前面 —— 所以无论怎么改掩码都表达不出"LFE 在 FC 之前"。

这是硬件/固件的写死顺序。修复只能在软件侧做，用 ffmpeg 交换第 3、4 通道：

```bash
ffmpeg -i in.wav -af "pan=5.1|c0=c0|c1=c1|c2=c3|c3=c2|c4=c4|c5=c5" \
       -c:a pcm_s24le out.wav
```

> 修通道输出是 24 bit；验收只针对采集 WAV，对 `_fixed.wav` 会 `format-fail`。

对视频文件（视频流不重编码）：

```bash
ffmpeg -i in.mkv -af "pan=5.1|c0=c0|c1=c1|c2=c3|c3=c2|c4=c4|c5=c5" \
       -c:v copy -c:a pcm_s24le out.mkv
```

## 七、在 OBS 里录制

OBS 的「视频采集设备」源自带音频走 **DirectShow，只有 2 声道**。
6 声道必须用独立的 WASAPI 音频源：

1. `设置 → 音频 → 声道 = 5.1`，采样率 48 kHz
2. 视频源（或显示捕获）的音频输出模式设为「无」
3. 另加 `音频输入采集(WASAPI)` 源，设备选采集卡
4. `编辑 → 高级音频属性` 只勾轨道 1

实测 OBS 33 可录 **4K120 hevc + 6ch pcm_s24le**，音频无损。
录完用第六节的命令做一次通道重排（视频流直接复制，很快）。

## 八、风险与回退

| 风险 | 说明 |
|---|---|
| 描述符结构错误 → 设备无法枚举 | 用 `tooling\reverse\uac_desc_lint.py` 预检；只改 USB3 那份配置，USB2 那份留作退路 |
| 刷写过程断电 | 会损坏固件，但硬件通常不坏，重刷即可（需要能访问 Flash 的工具） |
| Windows 缓存旧端点格式 | 每次改描述符都要同时改序列号 |
| 插到 USB 2.0 口 | 会退回原厂配置（2 声道），**不会损坏**，换回 USB 3 口即可 |

**回退到原厂**：刷 `firmware\release\ms2130s_backup.bin`，序列号也会还原。

如果刷成了"无法识别的 USB 设备"（描述符结构非法，Windows 连接口都不给），
Windows 侧就完全无解了（设备连 VID/PID 都不上报，任何驱动都绑不上）。
这时需要**用 Linux 裸控制传输**救砖：Ubuntu 启动盘 + `/dev/bus/usb` +
`USBDEVFS_CONTROL` 直接发 HID 类控制传输，先
`echo -n *:1.4 > /sys/bus/usb/drivers/usbhid/unbind` 解绑内核驱动，
再刷回原厂固件。本仓库的 `tooling/reverse/ms213x_restore.py` 实现了这套流程。

---

## 九、适用性

- 适用于 **MS2130S / MS2131S** 且固件里存在 `alt3 = 6ch` 描述符的采集卡
- 判断方法：读固件，搜索 UAC1 Format Type I 描述符
  （字节模式 `0B 24 02 01 06 02 10 01 80 BB 00`，其中 `06` 是 bNrChannels）
- 不同批次固件的偏移可能不同，`tooling\reverse\mk_alt3_usb3only.py` 是按描述符结构解析的，
  不依赖固定偏移

## 十、结论

固件按 alt 序号查表，Windows 只暴露一个 alt。做法只有一个：
让 alt3 成为唯一可选项。

整件事没有破解任何加密，没有逆向协议，改的是厂商自己写好的、
只是没让它生效的那份描述符。
